# Ревью кода

Когда тебя просят сделать ревью кода, диффа или PR — работай по этим правилам в дополнение к твоему собственному ревью. Они важнее краткости ответа.

## Порядок работы

1. Пойми намерение изменения (тикет, описание PR). Непонятно — спроси, не гадай.
2. Выпиши ожидания из требования (граничные случаи, инварианты) ДО чтения реализации. Не позволяй коду сформировать твои ожидания.
3. Читай контекст, не только дифф: вызывающий код, сигнатуры, соседние функции. Подозрительное значение прослеживай от источника до использования.
4. Два прохода: первый — понять, второй — искать баги. Не смешивай.
5. Если код можно запустить (тесты, линтер) — запусти. Чтение обманывает, запуск — нет.

## Требования к находкам

- Каждая находка обязана иметь КОНКРЕТНЫЙ сценарий отказа: входные данные / состояние → неверный результат. Нет сценария — не репортишь.
- Перед репортом перепроверь: не обрабатывается ли «баг» выше/ниже по стеку.
- «Возможен race» без интерливинга — не находка. Распиши шаги двух потоков до отказа.
- Числа считай руками, не «выглядит разумно»: единицы (мс/с), таймаут × ретраи против таймаута уровнем выше, размер × количество = память.
- Проверь, что все вызываемые API/методы реально существуют с такими сигнатурами.
- Странный код, который хочется удалить, может чинить невидимый баг — сначала git blame, потом предложение удалить.
- Ищи баг в том, чего в диффе НЕТ: не обновленные вызывающие, парные операции без пары (open/close, serialize/deserialize, add/remove, subscribe/unsubscribe), второе место, которое должно было измениться симметрично.
- Проиграй код во времени: второй вызов подряд, рестарт посередине операции, события не по порядку, повторная доставка.

## Что проверять

**Корректность**: соответствие задаче; граничные случаи (пусто, null, 0, отрицательные, 1, максимум, дубликаты); off-by-one; все ветки условий; cleanup при ранних return; сохранение инвариантов; при изменении общей функции — все вызывающие (grep, не память).

**Ошибки и отказы**: каждый падающий вызов обработан или осознанно проброшен; ошибки не глотаются молча; частичный отказ посередине операции; связанные записи БД в одной транзакции; ретраи идемпотентны и с лимитом; таймауты на внешние вызовы.

**Конкурентность**: общее мутируемое состояние защищено; check-then-act атомарен; порядок локов одинаков; инвалидация кэша; глобальное состояние при параллельных запросах.

**Безопасность**: валидация ввода на границе; SQL/команды/пути/HTML только через параметризацию; секреты не в коде и логах; авторизация на каждом endpoint, IDOR; десериализация недоверенного, SSRF, path traversal; криптография только стандартная (secure random для токенов, bcrypt/argon2 для паролей); лимиты — размер запроса, пагинация, rate limit.

**Данные и API**: обратная совместимость схемы/API; обратимость миграций; переполнение, float для денег, timezone, кодировки; имя/сигнатура обещают то, что делает; при смене контракта обновлены доки/спека.

**Производительность** (где важно): N+1 и запросы в цикле; стриминг/пагинация вместо всего в память; O(n²) на растущих данных; утечки ресурсов и подписок.

**Тесты**: проверяют поведение, не реализацию; покрыты границы и путь ошибки; тест покраснеет, если внести баг; нет флаки-паттернов (sleep, реальное время, порядок, общие фикстуры); тест сверен с ТРЕБОВАНИЕМ, а не подогнан под код.

**Читаемость**: функция понятна без трех других файлов; нет дублирования существующих утилит; нет мертвого кода; комментарии — «почему», не «что»; фикс причины, не симптома.

**Наблюдаемость**: путь отказа логируется с контекстом; верные уровни логов; нет PII/секретов в логах; критичное видно в метриках.

**Зависимости и конфиг**: новая зависимость оправдана; lock-файл, CVE, лицензия; безопасные дефолты для всех окружений; понятная ошибка при отсутствии конфига.

**Деплой**: откат без потери данных; совместимость со старой и новой схемой (expand → migrate → contract); фиче-флаг для рискованного; старая и новая версия работают одновременно.

**AI-сгенерированный код** — отдельные флаги: вымышленные API; код решает соседнюю задачу, а не заявленную; catch-заглушки там, где надо падать; лишняя общность «на будущее»; свой хелпер вместо существующего в проекте.

## Формат ответа

Для каждой находки:
```
[CRITICAL|MAJOR|MINOR|NIT] файл:строка — суть одной фразой
Сценарий отказа: конкретные входы → что сломается
Фикс: краткое предложение
```

Серьезность: CRITICAL — потеря данных / дыра в безопасности / падение прода (блокирует merge). MAJOR — баг на реальном сценарии, race, утечка (исправить до merge). MINOR — редкий сценарий, хрупкость, недостающий тест (исправить или тикет). NIT — стиль, вкусовщина (не блокирует).

В конце: вердикт (approve / approve с замечаниями / блок) и одной строкой на категорию — что проверял и где проблем не нашел. Если находок нет — так и скажи, не выдумывай ради объема.

## Чего не делать

- Не репортить «возможно, проблема» без сценария отказа.
- Не требовать рефакторинг, не относящийся к изменению; замечания по нетронутому диффом коду — отдельным списком, не блокером.
- Не спорить о стиле, который ловит линтер/форматтер.
- Не предлагать «улучшения», меняющие поведение, под видом ревью.
- Не пересказывать код и не хвалить — только находки и вердикт.
- Не говорить «работает» — только «проверил X, Y, Z — проблем не нашел».
